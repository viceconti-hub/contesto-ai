## L'area assistenza: la catena canonica e il lead user

*Fatto maggiore del periodo. Il "grande cantiere" 15–29 agosto ha dato all'assistenza una catena scritta e strumentata:*

**richiesta reale → chiamata di servizio → attività → cockpit → Calendar → intervento → registrazione dalla chiamata (anticamera = offerta) → consegna di assistenza.** L'intervento senza chiamata è l'eccezione nominata, non una via. Ogni anello ha il suo strumento: le note smistate da n8n in `/NOTE/chiamate-di-servizio`; la chiamata creata nel client **o da Code da linguaggio naturale** (risolutore a chiave naturale → scheda attrezzatura); l'attività generata automaticamente (interruttore ProblemType); il Calendar sincronizzato via n8n; il modulo cartaceo che porta il **numero di chiamata come giuntura carta↔SAP**; l'offerta generata dalla chiamata come anticamera della consegna.

**Sette pipeline in esercizio**, tutte con lo stesso pattern (*input → parse → mappatura → dry-run → apply; lo script si ferma e non inventa*): chiamata→offerta (**39 chiamate evase → 38 offerte generate**); registrazione schede attrezzatura (**~60 in cinque giorni**, tre clienti caricati per intero, modalità anticamera per i massivi dallo storico); attività da chiamata (anche dal bottone SAP sul server); ordini d'acquisto REPA dalla mail di conferma; **offerta di vendita dal carrello vicecontistore** (primo caso CINOLO, 14.674 €); scritture massive anagrafiche; **documenti SAP da messaggi vocali** (chiamate, attività, eventi Calendar e il primo **ordine cliente da alias vocali** — 260421, righe risolte da "detersivi verde/blu").

**La spiegazione strutturale (progetto Formazione): l'area tecnica è il *lead user* dell'ecosistema** (von Hippel). È l'ambiente a massima entropia — eventi non programmabili, dati nati sul campo in forma disordinata, persone in movimento, urgenze vere — e le soluzioni che sopravvivono lì sono robuste per selezione: i pattern maturano nell'ostile e viaggiano verso gli ambiti ordinati, quasi mai al contrario. Prospero è insieme il lead user e il progettista che ne raccoglie le invenzioni. **Criterio di allocazione conseguente**: a parità di valore immediato, il cantiere nell'ambiente più difficile rende di più — il costo di configurazione lì compra opzioni su tutto l'ecosistema. **Prima verifica del viaggio di ritorno**: il documento-anticamera, temprato nell'assistenza, applicato al carrello e-commerce (l'ambiente più ordinato) a costo frazionale — ed è il ponte meccanico tra il pull marketing e la preventivazione.

**Dottrina consolidata** (custodia analitica nelle memorie del workspace): il **documento-anticamera** come pattern nominato — si procede prima della certezza, *il documento dichiara ciò che manca* (MATRICOLA DA SPECIFICARE, riga TESTO DA CODIFICARE), la certezza arriva dal campo e chiude l'anticamera; il **dry-run come lista della spesa** per l'anagrafica (dry-run e apply in due passi, mai concatenati); la **chiave naturale** cliente+tipologia(+modello) all'86% di univocità come porta d'ingresso vocale, con la matricola stella polare nei documenti; un campo esistente **promosso a dizionario** (Codice a barre = alias degli articoli ad alta rotazione); la grammatica chiusa che assorbe le scorciatoie reali; **gli strumenti li detta il campo** (niente viste finché un'esigenza reale non le chiede). **Cambio di natura dell'Hub**: il *registro* delle matricole passa alle Schede Attrezzature di SAP; l'Hub resta **giacimento** (cinque fonti di matricole censite) e deposito documentale per macchina. La scheda attrezzatura è l'**inventario del cliente**, oltre l'area tecnica.

## Il cantiere registro (infrastruttura trasversale)

Resta il **cantiere principale dichiarato**, con l'impianto della 2.0 (indice come cuore: esiste/dove/quanto fresca; ASSETS PRODOTTI con le tre regole; documento-di-prodotto vs di-esemplare; architettura per fornitore; matricola come chiave d'ingresso — ora *in esercizio* via schede SAP). Decisioni architetturali del periodo:

- **Apertura dal caso Morini prezzi** come prima pietra (strategia dei due livelli: disegno complessivo + piccoli obiettivi che lo informano); l'adattatore email Morini è nel backlog n8n. Prima la **ricognizione orientata** di Code sui materiali di gennaio (schema, script, riusi del volantino, divergenze), col criterio *il dato si eredita, il codice si giudica*.
- **Inversione di gerarchia**: il registro è l'infrastruttura primaria; la Pipeline PrestaShop ne è un consumatore.
- **SQLite confermato con criterio di uscita** (molti scrittori simultanei o scrittura via rete → PostgreSQL), con l'argomento nuovo dell'**affinità AI** (il database che i modelli conoscono meglio; Code lo manipola con affidabilità massima).
- **Politica descrizioni per fornitore come configurazione nel registro** (Morini: non sovrascrivere l'esistente; Rational: sovrascrivere perché veicola le successioni): campo descrizione-fornitore con data + campo arricchimento-utente — duplicazione consapevole per destinatari divergenti.
- **Principio registro-anticamera: propone, non dispone.** Il Service Layer resta la porta unica e permanente delle scritture SAP; il registro prepara, la conferma dispone, il fetch successivo certifica. Interfaccia anagrafiche SAP↔PrestaShop ridisegnata sul pattern **snapshot-nel-registro** (due fetch, una lettura, delta storicizzabili).
- **Tre memorie in tre substrati**: registro = dati (consumati da pipeline), wiki = concetti (consumati da intelligenze), handoff = episodi. Il criterio è il consumatore.
- **Listino remoto come proiezione statica del registro** (pagina rigenerata a ogni aggiornamento, pattern GitHub Pages): nessun servizio da tenere acceso. **FastAPI declassata a opzione congelata** (Render sospeso; GitHub raw via di default per il contesto).

## n8n: sistema note completo e autonomia supervisionata di Code

**Sistema note strutturalmente completo e in produzione**: ingressi multipli (AudioPen, gruppi Telegram, chiamate di servizio), pipeline unica, 13 categorie, radice **`/NOTE`** (le note hanno sorgenti multiple, non solo vocali); categoria **`chiamate-di-servizio` multi-tipo** a match multi-parola (6 tipi — rispecchia la natura multi-area del modulo SAP) come inbox del flusso end-to-end; **doppia destinazione assistenza** (archivio completo del team + elenco curato dalla parola-segnale — normalizzazione all'origine, tecnici inclusi). Error notifier attivo; credenziali tutte definitive OAuth2.

**Salto del 28/08: primo intervento di Code sui workflow via REST API** — 34 modifiche, zero errori, un bug preesistente scoperto e segnalato (né obbedienza cieca né decisione silenziosa), primo backup JSON dei workflow. Due lezioni elevate a principio: (1) **perimetro API/UI** — Code modifica la struttura, l'umano collauda e pubblica; le credenziali si depositano, non si estraggono (il principio capability incarnato); (2) **PUT su workflow attivo = deploy immediato** — prima violazione *strutturale* del principio dell'anticamera, da cui la regola generale: **quando lo strumento non offre un'anticamera nativa, il protocollo la ricostruisce; dove si sceglie di non ricostruirla, la deroga è una decisione esplicita, mai un default** (tre guardrail: disattiva-modifica-riattiva; copia disattivata con swap; deroga consapevole per modifiche piccole). Uso standard: modifiche meccaniche → Code via API con guardrail; logica nuova e collaudo → UI.

**Everything promosso a capability interrogabile**: un solo indice, due consumatori (Prospero alla finestra, Code via es.exe — read-only per costruzione); struttura cartelle = stato, segnalibro = vista; usato in ogni pipeline per il controllo matricola. *Il filo della settimana: uno strumento che serve a Prospero viene esteso a Code a costo quasi zero.*
